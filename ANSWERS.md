### Root cause and ORM explanation

The constructed root cause is an N+1 related-object query. Iterating the orders queryset evaluates one SQL query. Accessing each `order.items.all()` without a prefetch creates and evaluates another queryset for that order. Django's reverse manager does not infer a cross-order batch fetch, so 250 orders cause 251 business queries.

`fixed_data()` uses `annotate(total=Sum(...))` on the owner-filtered queryset. Django produces a `LEFT OUTER JOIN` to items and groups by the order's columns. `quantity * unit_price` is evaluated in the database and summed per order. The left join preserves orders without items; `Sum(default=Decimal('0.00'))` supplies the empty total. No related items are accessed in the serialization loop, keeping business query count at one. This shifts arithmetic and grouping to the database and avoids fetching item model instances. Decimal values are formatted consistently for JSON.

For a response that needed complete item records, `prefetch_related('items')` would instead fetch orders and items in two batched queries, using more application memory. `select_related()` is appropriate for single-valued foreign-key/one-to-one relationships, not a reverse item collection. Neither batching nor aggregation removes the need to constrain the owner and consider response size for very large accounts.

## Section 2 — Queue behavior and SIGKILL

See `DESIGN.md` for architecture alternatives, atomic Lua operations, fail-closed policy and retry/backoff decisions. Implementation lives in `mailqueue/`.

With `task_acks_late=True`, a successful task is acknowledged after execution. This setting alone is insufficient when a worker child is abruptly killed: `task_reject_on_worker_lost=True` asks a surviving parent to requeue that task. Killing the entire worker removes the parent's opportunity to reject; Redis visibility-timeout restoration and the database outbox/lease recovery then provide eventual redelivery. The configured timeout is 120 seconds, hard task limit 30 seconds and processing lease 45 seconds. Recovery is eventual, not instant.

If killed before sending, the job is retried after recovery. If killed after provider acceptance but before the database update, redelivery uses the same UUID idempotency key. The fake provider returns its saved receipt without sending again. This is at-least-once task execution with idempotent provider effects, not a general exactly-once guarantee. Durable job rows, periodic outbox dispatch and transactional dead letters account for every accepted job under the stated worker-crash failure model. Database/disk destruction is outside that model.

## Section 3 — Question A — Django Admin Performance

A primary-key index only helps queries that use it; it does not address every operation on a changelist. I would first profile an authenticated admin request and inspect repeated SQL, count queries and the selected ordering before changing settings.

First, `list_display` methods or related-object labels can create an N+1 query pattern. I would set `ModelAdmin.list_select_related = ('customer',)` for foreign-key columns, or override `get_queryset()` to use `select_related()` and `prefetch_related()` appropriately. A custom display method that calls a related manager's `count()` may instead need `annotate(Count(...))`. I would also inspect `__str__()` methods for hidden relation access. Larger joins and prefetched collections consume memory, so I would fetch only relationships the page actually displays.

Second, full-table counting can dominate latency. Setting `show_full_result_count = False` removes the additional unfiltered total shown by the admin. It does not eliminate the paginator's filtered `COUNT(*)`. If that count remains expensive, I would provide a custom paginator through `ModelAdmin.paginator`, using an explicitly approximate or capped count where the product permits it. The sacrifice is exact totals and potentially precise last-page navigation; overriding counts without explaining those effects would be misleading.

Third, the default search or ordering may scan or sort many rows. I would inspect `search_fields` for broad case-insensitive substring searches and use exact lookups such as `'=email'` where appropriate, with a matching database index and collation. I would review `ordering`, add a composite index matching common filters and ordering, and use `QuerySet.explain()` to verify the plan. For expensive foreign-key form choices, `autocomplete_fields` or `raw_id_fields` avoids rendering huge select boxes. Indexes cost storage and write performance, so measured query plans should justify them.

## Section 3 — Question B — Pagination Trade-offs

Offset pagination uses a query such as `ORDER BY created_at, id LIMIT 50 OFFSET 500000`. It supports page numbers, arbitrary jumps and familiar admin interfaces. However, a database generally still walks or processes the skipped rows; an index helps ordering but does not make a deep offset free. Exact total counts can add another expensive query. I would use it for modest datasets or reporting screens where direct page navigation matters and latency is acceptable.

Offset positions also change as records are inserted or deleted. During mobile infinite scroll, a new row inserted before the current offset can cause the next page to repeat an already-seen row; deletion can make a row disappear from the traversal. Stable ordering is necessary but does not eliminate position shifts between separate requests.

Cursor pagination records the last ordering values and seeks after them. For descending order by `(created_at, id)`, the next queryset uses `Q(created_at__lt=t) | Q(created_at=t, id__lt=last_id)`, orders by `-created_at, -id`, and takes the next limit. A matching composite index supports that access pattern. The unique ID breaks timestamp ties; ordering fields should be immutable. The server should validate or sign cursor contents and preserve the same filters and authorization scope on every request.

This fits infinite scroll because clients normally ask for the next page, and new rows before the cursor do not shift the seek boundary. It is not a snapshot: deletions, changes to sort fields and filter changes can still affect traversal. Cursor pagination sacrifices convenient arbitrary page jumps and exact page counts, and reverse navigation requires additional logic. For a large activity feed I would choose cursors; for a small, page-number-oriented internal listing I would usually choose offsets. If a consistent historical export is required, I would separately define snapshot or cutoff semantics.
